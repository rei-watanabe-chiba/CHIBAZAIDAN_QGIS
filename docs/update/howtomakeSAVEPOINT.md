# howtomakeSAVEPOINT.md

# LLM支援開発における SAVEPOINT（設計状態保持）構築・運用ガイド

## 1. SAVEPOINT 思想と全体概要

本ガイドは、大規模コードベースや複雑な PyQGIS プラグイン等の改修において、**LLM（AIアシスタント）の理解度・情報密度を最適化し、ハルシネーション（虚偽のコード生成）やデグレ（修正漏れ）を完全に防止するための標準設計手法**を定義したものである。

本手法では、仕様書を**「UI/UX ライフサイクル（縦軸: 制御・操作）」**と**「機能内部アーキテクチャ（横軸: データ・ロジック）」**の 2 軸に完全分離し、アンカーIDで強結合させる**「SAVEPOINT (セーブポイント) 方式」**を採用する。

```text
       【縦軸: UI/UX ライフサイクル】 (UIUXlifecycle.md)
       「いつ・どこで・どの画面/イベントが発火し、どう制御されるか (When & Where)」
                                  │
                                  │  🔗 アンカーID (FEAT-XX) で相互リンク
                                  ▼
      【横軸: 機能内部アーキテクチャ】 (FeatureArchitecture.md)
       「データがどう変換され、どのDB/オブジェクトにどう反映されるか (What & How)」
```

---

## 2. 2軸分離が生むシナジー構造

1つの巨大な仕様書（オールインワン資料）にまとめず、あえて 2 ファイルに分離する理由は、**LLMのコンテキストウィンドウ利用効率と情報密度の「スイートスポット」**を狙うためである。

| 観点 | 巨大単一ファイル (All-in-one) | SAVEPOINT 方式 (2軸分離 + アンカー強結合) |
| :--- | :--- | :--- |
| **LLMの理解精度** | 情報が埋もれ、不要な文脈まで読み込みハルシネーションが発生しやすい | タスクに応じて必要な軸（UI制御 or データロジック）に焦点を絞れ、高精度 |
| **影響範囲の特定** | UIの変更がどの内部ロジックに響くか曖昧になりがち | アンカーID (`FEAT-XX`) を辿ることで、画面からロジックへ 360 度双方向追跡可能 |
| **保守性** | 画面の見た目を変えただけで全体を書き直す必要が生じる | UIの変更は `UIUXlifecycle.md`、計算ロジック変更は `FeatureArchitecture.md` のみ更新で済む |

---

## 3. LLM理解度の「スイートスポット」を突く4大要点

LLMがユーザーからの改修指示を受けた際に、一切の迷いなく一発で正確な修正案を出せるようにするための要点である。

### ① アンカーIDによる強結合 (Shared Anchor IDs)
* **要点**: UIコンポーネント（例: `MainDockWidget`）とドメイン機能（例: `FEAT-01: POINT_DIGITIZING`）に共通の ID を付与する。
* **効果**: LLMは「`MainDockWidget` の変更 ➔ `FEAT-01` のロジックも確認が必要」と即座に文脈を統合できる。

### ② Source of Truth (真実のデータ源) と同期タイミングの階層化
* **要点**: データが「Primary (DB)」「Secondary (Memory Cache)」「Render Output (キャンバス)」のどこに存在し、いつ同期されるかを明記する。
* **効果**: QGIS 開発特有の「メモリだけ更新して GeoPackage に保存し忘れる」「レイヤは更新したが `triggerRepaint()` を呼び忘れて画面が更新されない」といったバグを防ぐ。

### ③ 破壊不可制約 (Invariants) の強調表記
* **要点**: 「座標系の軸反転ルール（$X_{survey}=Y_{math}, Y_{survey}=X_{math}$）」や「トランザクション境界」など、リファクタリング時に**絶対破ってはならないアルゴリズム上の掟**を太字・警告で宣言する。
* **効果**: LLMが「コードを綺麗にしようとして、必要な座標変換処理を消してしまう」事故をシャットアウトする。

### ④ 二重の影響波及マップ (Impact Matrix)
* **要点**: UI側からの波及（ボタン非活性、モーダル停止）と、機能側からの波及（別機能のレンダラー再評価、CSV出力ヘッダー影響）の両面で影響先をリスト化する。
* **効果**: 1箇所の修正に伴う連鎖的なデグレを、LLM自身に事前に検知・警告させることができる。

## 4. エージェントの思考・調査ガイドライン (Deep Code Analysis Rules)

表面的な「ボタンを押すと関数が呼ばれる」という正常系の処理フローだけでなく、裏側にある真のシステム仕様を抽出し SAVEPOINT に反映させるため、エージェントはコード調査時に以下の4つの観点を必ず検証・言語化しなければならない。

### ① 【機能間競合と副作用の修復ロジック】の探索義務 (Cross-Feature Collisions)
* **要点**: ある機能の更新（例：環境設定の適用）が、他機能の状態（例：フォーカスモードの透過度）を破壊していないか確認する。
* **行動**: 破壊を防ぐ「自己修復メカニズム」や「再適用ロジック」を発見した場合は、必ず `FeatureArchitecture.md` の Invariants に記載し、影響波及マップに反映すること。

### ② 【非侵襲的UXとフェイルセーフ】の言語化 (Non-invasive UX & Safety Guards)
* **要点**: エラー時にポップアップを出さずにクリックを静かに無視する（サイレントブロック）仕様や、特定条件で物理的にボタンをグレーアウトさせる仕様など「引き算のUX」を評価する。
* **行動**: ユーザーの誤操作をどう防いでいるか（何が起きないか）を、`UIUXlifecycle.md` の【状態・排他制御ルール】として明記すること。

### ③ 【OS・インフラレベルの物理制約】の Invariants 化 (Infrastructure Constraints)
* **要点**: Windowsのファイルロック（WinError 32）回避策や、SQLiteのトランザクション制限、QGIS C++エンジンの描画ライフサイクルなど、インフラに起因する泥臭い制約を見逃さない。
* **行動**: これらの回避策（ワークアラウンド）を見つけた場合は、絶対に壊してはならない Invariants として赤字レベルで記載し、リファクタリング時の事故を防ぐこと。

### ④ 【不可視の座標変換とライフサイクル】の追跡 (Implicit Coordinate Transformations)
* **要点**: マップキャンバスツール等は単なるクリックリスナーではなく、「スクリーン座標 ➔ マップ座標 ➔ ピクセル座標 ➔ 測量座標」という複雑な変換を担っている。
* **行動**: データの出入り口で座標系がどう逆算・変換されているかのライフサイクルを厳密に追跡し、計算式やアフィン変換の適用箇所をアーキテクチャとして明記すること。

## 5. SAVEPOINT の構築・運用サイクル

大規模改修を行う際は、以下の 3 ステップで SAVEPOINT を最新化・維持する。

```text
[1. ロード (Read)] ➔ 改修前に LLM へ `UIUXlifecycle.md` と `FeatureArchitecture.md` を読み込ませる
[2. 実行 (Execute)] ➔ 指示に基づき、影響範囲マップを確認しながらコードを改修する
[3. セーブ (Update)] ➔ 改修完了後、変更されたシグナル・データ構造・UI仕様を SAVEPOINT ドキュメントへ反映する
```
