# Core Architecture & UI/UX Principles

プラグイン全体の根幹アーキテクチャおよびUI/UXの絶対的な設計思想・制約（Invariants）を定義する。

## 1. モジュール責務の境界定義 (MVC/MVVM)
機能追加時はこの境界を越えた依存関係（スパゲッティ化）を作ってはならない。
* **UI層**: 画面表示とユーザー操作のオーケストレーション。状態保持・バリデーション。
* **永続化層**: 空間データ等永続化、状態ファイル操作、描画状態管理。
* **ドメイン層**: 外部キャンバスや特定のUIフレームワークに依存しない、純粋なドメインロジック。
* **キャンバス層**: メインキャンバス上の入力イベント受付のみを担当する純粋な入力モジュール。

## 2. 単一方向のシグナル・イベント駆動設計
* **入力モジュール ➔ UI**: 入力モジュールはUI状態を参照せず、イベントを発行するのみ。
* **UI ➔ 入力モジュール**: 状態変更はUIからの一方通行の通知として行う。
* **ネイティブシグナルへの描画委譲**: 属性変更や要素削除などのデータ更新時は、手動の `triggerRepaint()` や `canvas.refresh()` による多重再描画を禁止する。QGIS本来のシグナルに描画を委ねることで、描画フリッカーを解消する。
* **シグナルループの遮断**: プログラムからUIコンポーネントの値を更新する直前には必ず `blockSignals(True)` を呼び出し（更新後に解除）、イベントハンドラの無限ループや不要なシグナル発火を防止すること。

### 2-1. 中央ディスパッチャーによるアクション処理パイプライン
UIから発行される「確定した意思決定」は、画面ごとの処理担当（Controller）が個別にバラバラな作法で捌くのではなく、単一の中央ディスパッチャーを必ず経由させる。中央ディスパッチャーは、確定操作ごとに散在しがちだった以下の処理列を一括して仲介する共通パイプラインとして機能する。
* **【前置バリデーションの一元化】**: 操作の確定前に満たすべき検証ルールをディスパッチャー側にまとめて登録し、実処理に入る前にそこで判定する。検証に失敗した場合は実処理を呼び出さず、エラー状態のみをUIへ即時反映して処理を打ち切る。
* **【大域ビジー制御の自動付与】**: 実処理の開始直前と終了直後に、処理中状態への切り替えと解除を自動的に行う。画面ごとの処理担当が自前でロックの設定・解除漏れを気にする必要はない。
* **【横断的な例外捕捉】**: 実処理の中で発生した例外は、ここで一括して捕捉されログに記録されたうえで、UIの安全なエラー表示へ変換される。個々の処理担当が例外処理を書き漏らしても、画面がロックされたまま固まることはない。
* **【処理結果のバッチ反映】**: 実処理が返す複数の状態変更意図は、UIの不変状態ストアへまとめて適用され、まとまった1回の通知として差分描画へつながる。
* **【未登録操作のローカル受容】**: すべての操作をこのパイプラインへ通す必要はない。コンボボックスの選択変更やキャンバス上のホバーなど、軽量かつ確定前のUIイベントは、各画面が直接受け止めてよい。パイプラインに登録されていない操作は、素通りでそのままUIの不変状態ストアへ渡される。
* **【宣言的UIとの自動結線】**: 宣言的に構築されたパネルが持つクリックや値変更などのイベントフックは、画面側で個別にコールバックを書かなくても、対応する操作として自動的に組み立てられ、中央ディスパッチャーへ送出できる仕組みが用意されている。これにより、UI層と処理担当の間で巨大な手動の対応表を都度書く必要がなくなる。

### 2-2. 大域ロックと局所ガードの使い分け
画面ロックは「大域ロック」と「局所ガード」を処理の規模と文脈に応じて使い分け、過度な一元化による応答性の低下や操作性の不全を防ぐ。
* **【大域ロックを用いる場面】**: ファイルI/O、重い座標変換計算、セッション読み込みなど、非同期的・長時間で影響範囲の広い処理には、中央ディスパッチャーが自動的に付与する大域ビジー状態を用いる。アプリ全体（カーソル・ドック・キャンバス）を一括して待機状態にする。
* **【局所ガードを用いる場面】**: キャンバス上の単発打刻や属性の一時反映など、短時間かつ特定の文脈に閉じた連続操作には、中央ディスパッチャーを介さず、その場で完結する軽量なガード（処理の前後で自前に処理中フラグを立てる仕組みや、入力モジュール単位の操作ロック）を用いて同期的に画面・キャンバスを保護してよい（「処理中のインタラクション安全ロック」参照）。

## 3. UI構築の絶対ルールとOSネイティブ保護
* **フレキシブルレイアウト強制**: デザインツールによる静的レイアウト定義を禁止。親コンテナの動的レイアウト設定（比率指定など）に伸縮を依存させること。
* **OS標準UIのハック禁止**: OS標準UIの挙動破壊防止のため、特殊なスタイルシート指定によるハック等は禁止。コントロールの状態変化は、実体ファイルの動的な参照先変更などで表現すること。

## 4. UX設計思想 (コンテキスト・スイッチングの排除)
* **常時展開の原則**: 折りたたみ方式等によるUI要素の隠蔽を禁止。全ての操作要素を常時展開させる。
* **視線移動の最小化**: 入力操作中の付随的なダイアログポップアップは、操作対象となる座標の近傍に出現させる。
* **非侵襲的なフェイルセーフ**: エラー時は操作を阻害するダイアログを出さず、「UIの視覚的警告表示とクリックイベントの静かな破棄」で対応する。
* **状態の排他制御**: 設定や出力などのダイアログ（非モーダル）操作中は、メインキャンバスでのデータ入力ツールを強制的に待機状態にし、誤操作を防ぐ。
* **処理中のインタラクション安全ロック (busy_interaction_guard)**: フィーチャ操作や画面更新など重い処理の実行中は、誤発火を防ぐためキャンバスのイベントをロック（カーソルをWaitCursorに変更）し、UIウィジェット全体を無効化(`setEnabled(False)`)してステータスを「処理中」にする。

## 5. UI/UX ライフサイクル制約

### 5-1. 宣言的UI構築とコンテナ主導サイジング (DRY徹底)
* デザイン生成ツールによるファイルを排除し、プログラミング言語上での宣言的なUI構築を採用する。
* UI表示テキストは専用の定数管理モジュール群で一元管理し、ロジックと文字列定義を完全に分離（DRY化）する。
* **【レイアウト規則の厳格化（親コンテナ依存の原則）】**
  * UI部品の縦横比や整列は親コンテナの比率設定などで統制し、固定値指定による微調整を禁止する。ウィジェット自身ではなく、**親コンテナの動的レイアウト**に伸縮を完全に依存させる。
  * **【パネル折りたたみ廃止と余白の一元管理】**: パネルのアコーディオン（折りたたみ）機能を全廃し、「ヘッダー文字の有無を動的に切り替えられるフレキシブル・セパレーター」でUIを分割する。UIの上下余白は定数(`SEPARATOR_MARGIN`等)により厳密に一元管理する。
    * **例外（Tab2 点情報パネル・属性パネルの統合表示）**: FEAT-01の点情報パネルと属性パネルは、関連性の強い一続きの入力操作であるため、意図的にセパレーターを挟まず視覚的に一つのパネルとして連続表示する。ロジック上は引き続き別々のPanelSpec/BuiltPanelとして管理される。

### 5-2. OSネイティブUIの保護とスタイル適用パターン
一般的なボタンやトグルは親コンテナに追従させる。**数値入力などの特殊ウィジェット**にスタイルを適用する場合、以下の検証済み安全パターンに限定すること（スタイル生成モジュール参照）。このパターン外の指定（特に部分的な部品の独自描画）はOS標準UIを破壊する可能性があるため厳禁とする。
1. **内部サブコンポーネントには配置位置を必ず明示指定する**。これを省略すると、部品が視覚的に分離し、クリック判定領域もズレてユーザーの操作を受け付けなくなる。
2. **特殊な視覚要素はスタイルシートのトリック（透明化による疑似図形など）で描画しない**。フレームワークの実装においては信頼性がなく、表示崩れ等の不具合を起こす。
3. **画像要素はインライン化されたデータ文字列（Base64等）で指定しない**。フレームワークのサポートが不完全な場合があり、要素が完全に非表示になる。画像はリソースディレクトリ配下に実ファイルとして配置し、スタイル生成時に絶対パスを動的計算して参照すること。
4. **押下時などのユーザーアクションによる状態変化フィードバックは、ウィジェット全体の背景色ではなく画像リソース自体の差し替えで表現する**。背景色を状態に応じて変化させると、フォーカス枠など他の視覚要素との競合を誘発しやすく、状態の組み合わせごとに個別のケアが必要になる。内部画像のみの変更であれば、他の要素に影響を与えず、この種の問題が発生しない。
5. ユーザー操作による状態変化のルールでは、幅・高さ等のプロパティがシステムから引き継がれない場合があるため、変化後の状態でも必要なプロパティを明示的に再定義し、システム状態との乖離を防ぐこと。
